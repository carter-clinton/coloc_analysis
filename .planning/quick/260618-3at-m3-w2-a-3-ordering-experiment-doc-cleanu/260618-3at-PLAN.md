## Context / decision (authoritative)

The cluster ordering experiment (`scripts/a3_blockmatrix_lowering_repro.py`) ran on a
**16-worker resize** of cluster `20260617` (`--skip-old --n-var 130000 --n-samples 2000
--radius-bp 1000000 --budget-sec 3600`). Outcome:

- **Ordering A COMPLETED** — 928.0 s, shape (130000,130000), valid `A/repro_A.bm`. **First
  cluster validation of the deployed A.3 fix** (dev-10 paused before ever confirming it).
- **Ordering B COMPLETED** — 863.5 s, valid `B/repro_B.bm` (hang-free; the `sparsify→checkpoint`
  IR-shape did NOT reproduce the OLD driver-collect hang).
- **Backend** `MASTER=yarn`, 64 concurrent tasks across 16 nodes. The 2→16 resize succeeding
  diagnosed the original 24-worker failure as **quota/size-bound, not project-level**.
- **DECISIVE FINDING (`--report-scratch-size`, full manifest):** `banded(B) == dense(A)` for
  **all 23 A.3 regions**, not just the worst. The manifest sets `radius = span+500kb` (capped
  50 Mb), which is always ≥ span/2, so the band covers ~the whole region everywhere. **Ordering
  B saves scratch NOWHERE** under this radius scheme.

**Decision: KEEP ordering A (deployed + now cluster-validated). Do NOT land ordering B** — it is
byte-identical numerics with zero scratch benefit and nonzero change-risk. CR-01's ~1.8 TiB
worst case is **ordering-independent** (region_00145 needs it under A or B); the real GATE-3
question is xlarge dense-materialize **compute cost vs region-splitting**, not checkpoint ordering.

Cluster `20260617` being Stopped (not deleted).
