## What happened (settled mechanism)

lazy → that call is cheap and **passes**), then freezes at the **first action**, `count_cols`, which
materializes the genome-wide plan. Direct thread evidence (jstack ×2 + `/proc` + py-spy-class probes):
- **Driver JVM:** NO `is.hail`/GCS/executor thread running — every RUNNABLE thread is an idle
  `EPoll.wait` event loop; `ClientServerConnection` threads in `waitForCommands`; flat CPU. (`main` in
  `FileInputStream.readBytes` on stdin is the **liveness watcher**, a red herring — not the command path.)
- **Python kernel:** main thread in **untimed `recvfrom`** on the Py4J gateway socket.
- ⇒ **Both sides idle-waiting = a mutual wait at the Py4J boundary.** Deterministic at the same point on
  `_0003` and `_0004`.
- **Ruled OUT:** slow driver plan (JVM would burn `is.hail` CPU — it doesn't), GCS, requester-pays,
  any config knob, and a Py4J heartbeat (Py4J has **no default read timeout**; the untimed `recvfrom`
  is the *normal* "Java call in progress" posture, not a desync).

## NEXT = `/gsd-debug` — open it pointed at these two hypotheses + one fix candidate
- **H1 — stdout/stderr pipe-buffer deadlock.** The `SizeEstimator` reflective-access warning **flood**
  fires right before the freeze. If that log volume fills the JVM→kernel pipe faster than ipykernel
  drains it, the JVM blocks on a full pipe and Python waits forever (masked at chr22's smaller volume).
  **Untested discriminator the captures never ran:** is ANY JVM thread blocked in
  `FileOutputStream.write`/`writeBytes` to the log/stderr fd? (Needs a fresh small repro to confirm.)
- **H2 — Py4J lost-response.** The action's Java call returned but the response wasn't delivered, so no
  `is.hail` thread remains yet Python still waits.
- **Mechanism-agnostic FIX candidate (probably the real fix):** **per-chromosome checkpoint loop** —
  filter→action→checkpoint per chromosome and union, bounding each action exactly like
  `interval_filter="chr22"` did in Gate-C (which **never** wedged). If H1, it also slashes per-action
  log volume. **KEY CLUE:** Gate-C ran `read_matrix_table` on the **same** full genome-wide MT then
  pruned to chr22 partitions; the ONLY differing variable genome-wide is **`interval_filter=None`**
  (the full autosomal partition count the first action must materialize).
